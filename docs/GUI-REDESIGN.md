# GUI Redesign: Current Contract

> Current scope (2026-10-11): [Extensions only](EXTENSIONS-ONLY.md) supersedes every account-management, authentication, launch-command, account-credential, and assistant-lifecycle requirement below. Earlier implementation and acceptance entries are historical; they do not authorize these operations or establish acceptance of the new scope.


**Product positioning follows the [Multi-Account Parallel Design](MULTI-ACCOUNT-DESIGN.md) (decision dated 2026-09-28).** This document continues to govern the data model, write protection, and resource-domain behavior. Switching the main configuration to third-party connections, the saved connection library, default-environment cards, runtime-settings forms, overview, operation-history page, command-palette switching entries, and a separate Hooks page are retired under Appendix A of that design. Their UI and engine commands were removed on 2026-09-28; the corresponding sections below remain historical records. If the documents conflict, the multi-account design takes precedence.

## Data model: the actual configuration is authoritative

Each assistant's real files and directories are the **sole source of truth for active configuration**. The tool's data is divided into three layers:

| Layer | Content | Location |
| --- | --- | --- |
| Actual configuration | All active configuration: connections and runtime parameters, MCP entries, rule files, hooks, skill directories, and alias blocks | Real assistant files/directories |
| Saved but inactive | Alternatives explicitly saved by the user that the real environment cannot represent: inactive connection configurations, disabled Claude MCP entries, inactive rule templates, and instance definitions | `native-manager.db` |
| Built-in recommendations | Official connection presets, recommended skill sources, and hook-cleanup suggestions | Compiled in, read-only; never automatically written to the database or assistant environment |
| Source content | Recommended rules (`rules/*.md` in skill sources) and shortcuts (`aliases/*.json`) | Content repositories such as agent-skills, fetched through skill sources; read-only, never stored in the database, with item-by-item confirmation before application |

`native-manager.db` otherwise stores only application preferences (`app_settings`), the tool's own knowledge such as assistant recognition definitions and pricing, and ownership records (location + digest). It is not the source of active configuration and does not keep another copy of active content as the "current configuration."

- **Reads**: UI displays, status, and form prefilling always read actual configuration. Queries and status are read-only and perform no writes.
- **Writes**: Editing an active item writes directly to its actual file, changing only keys, entries, or blocks owned by this tool. Before writing, reread the actual content and compare it with the content when the editor opened. A mismatch reports "Modified externally" and refreshes; never overwrite silently.
- **Switching**: Before activating another saved alternative (rule template), backfill actual content into the current item, or save a backup if it matches no saved item, then write the target. Connection configurations are no longer written into the main configuration (see "Main Configuration Contains Only Official Accounts"). External edits are therefore preserved by default; "takeover = overwrite from the database" is no longer the only route.
- **Built-in recommendations**: Appear only as "Recommended · Apply," require individual confirmation, and show differences from actual content before application. They do not count as "Pending sync," enter bulk synchronization, or become database records on first run.
- **First run**: Existing actual configuration is the current configuration. Reads remain write-free; the main account only reports whether it is an official account. A missing database record does not make built-in defaults active configuration.

Settings are written to `app_settings`; policy writes always use `--layer local`. The UI does not provide a raw policy editor.

**No markers in assistant configuration.** Only officially supported fields and files may be written into each assistant's configuration: no custom keys such as `_MANAGED_BY`, management variables in `env`/`environment`, ownership comments, or manager files in assistant configuration directories. "What this tool wrote" is recorded only in `native-manager.db`: each write location records a file, key path, entry name, signature, or provider id so later writes can remove items no longer present in the definition. Every write is an explicit user action on a specific entry or file and compares against the write baseline `base` returned by status; external edits after opening cause rejection. The tool neither overwrites in bulk nor changes keys the user did not ask it to change. Legacy markers are recognized and stripped only when reading; they no longer establish ownership and are never written again. They are cleaned up only when the user explicitly applies that entry, never through bulk startup rewrites. Shell aliases are the sole exception: rc files are not assistant configuration and have no suitable structured fields, so paired block comments still delimit managed blocks.

Queries and status must be read-only and write-free; reading without a database must not create one. Saving an inactive alternative writes only to the database and performs no linking or refresh. Editing an active item writes directly to actual configuration as described above. Resource action buttons directly invoke real `apply`; internally, `apply` performs preflight/write checks, then executes and audits using exact scope, exclusive locking, external-change detection, CAS, and conditional rollback. Normal synchronization, enable/disable, and updates require no second confirmation; destructive actions such as removing definitions and clearing logs still require separate confirmation.

Resources such as Skill and MCP, and their per-assistant assignments, require add, edit/update, enable, disable, and delete operations. AI CLI definitions are the exception: the ordinary UI maintains only connections, runtime parameters, and account instances. Installation, upgrades, uninstallation, and complete definition editing are no longer product entry points; the original installation channel owns the software lifecycle. Existing lifecycle fields and engine capabilities remain in phase one for compatibility only, rather than as current product commitments.

Public `*:plan` and `--dry-run` entry points are retired and rejected.

## Import Existing Configuration (system:discover)

Assistant CLIs and skills already installed locally but not yet managed are classified by origin before bulk takeover. MCP entries remain authoritative in assistant configuration files and are viewed and edited directly on the MCP page, without importing here. Under the management model ([Multi-Account Design](MULTI-ACCOUNT-DESIGN.md), section 2.1), these appear in two places: unregistered assistants at the bottom of the Accounts page, and skills under "Unmanaged" on the Sources page. They are hidden when no actionable content exists and no longer occupy a separate page or settings entry. Classification directly determines the available actions:

| Origin | Detection | Handling |
| --- | --- | --- |
| Real directory inside an assistant's official skill directory | Not a symlink, such as Claude `synced/` | Identify only; retain its native installation mechanism, without takeover or overwrite |
| Symlink to an external path | Target outside the managed base directory, with a name outside defined collections | Group by source root into local source collections and manage the symlinks |
| Unplanned link belonging to a defined collection | Name matches a skill discovered through `skill_paths`, or each path's final component before the source is fetched | Use the existing collection takeover path (`--allow-takeover`) |
| Unbound link inside the managed base directory | Target inside `repositories`/`skill-versions` | Legacy residue; suggest cleanup only |
| Broken link | Target does not exist | Suggest cleanup only; never delete automatically |
| Installed assistant CLI with no definition | Known executable resolves through PATH or `~/.local/bin` | Register only the definition needed for recognition and configuration; retain the original channel for installation, upgrades, and uninstallation |

`system:discover` is read-only, write-free, network-free, and does not acquire the apply lock. Assistant candidates reuse the same origin classifier and bounded `--version` probe as `agents:status`. Takeover introduces no new write path: assistant registration writes definitions only; skills use the existing real skill-domain `apply`, retaining locking, external-change detection, CAS/conditional rollback, and auditing.

Local source collections (`source_path` in a skill collection definition, mutually exclusive with `url`) do not snapshot content. Links in assistant directories point directly to registered source directories; external tools still maintain and update their content. Disabling removes only links, without deleting or rewriting the external source. Only after registration do links to that root enter the managed baseline and become eligible for overwrite or removal on disable. Unregistered external paths remain fail-closed. The source must be an existing real directory. It must not be a symlink, reside inside the tool's data directory, or overlap any assistant skill directory.

If a source has been fetched and discovery succeeds but an assigned skill is missing because upstream removed it, each assistant offers only "Remove" for that skill. Remove the assignment and, if the entry is still a tool-created link, remove that link too. An external link requires explicit takeover; real files or directories are rejected. Actions are independent per assistant; enable, disable, and update are rejected. A missing skill in an unfetched mirror or failed discovery does not prove upstream removal and must not produce a removal suggestion. The overview lists such skills with missing links under "Your decision needed"; "Handle" opens "All skills" and searches for the skill directly.

## MCP Native Domain State

Actual entries in assistant configuration files are authoritative for MCP (see the [MCP Configuration Guide](MCP-CONFIG-GUIDE.md)). `mcp:status` is read-only and write-free: `targets` lists assistant MCP configuration files; `elements` groups same-named entries across assistants by service name, even when their content differs. Each entry provides sanitized modeled fields (env/header references unchanged, literals masked), unchanged unmodeled official fields, enable/disable state, and digest `base`. All existing user entries are visible and actionable without import.

`mcp:apply` operates on individual entries: `add`, `edit`, `enable`, `disable`, `remove`, `copy` (to another assistant, requiring explicit replacement if the target name exists), and `forget` (remove a saved definition not yet written to any assistant). Every write includes the entry's `--base` from when the operation opened, then rereads and checks under lock. A mismatch reports "Modified externally" and leaves files and database unchanged. Editing changes only modeled fields, preserving other official fields, comments, and tables in the entry (Codex uses `toml_edit` for in-place edits). Deletion requires separate confirmation.

Once add/edit form input is valid, read-only `mcp:preview` uses the same plan as writing to show each complete resulting target file. Copying to another assistant likewise shows the complete converted target file whenever the target or replace checkbox changes; an existing same-named entry still requires explicit replacement confirmation. The deletion dialog shows the complete post-deletion target file; deleting only saved disabled content explains that assistant files remain unchanged. Preview failure prevents confirmation. Raw previews may contain credentials and are displayed locally only, never stored in the database. Input changes immediately invalidate old results; execution still rereads and validates under the `mcp:apply` lock.

Disabling Codex/OpenCode writes the official `enabled = false` and retains the entry in the file. Claude Code has no global per-entry disable field: disabling removes the entry and stores a disabled snapshot (`mcp_saved`); enabling restores that snapshot and rejects an existing same-named target entry. Snapshots never store suspected credentials in plaintext: env literals matching credential detection and all header literals are moved to a user-selected external secret file and replaced by `${VAR}`. Without a usable selected file, disable is rejected. Ordinary literals not detected as credentials, such as `NODE_ENV=production`, are preserved in the snapshot. Forms may write ordinary new env values directly into configuration, never the database; suspected credentials are rejected with instructions to use `${VAR}`. Detection considers value formats (common vendor token prefixes) and variable names. SECRET, PASSWORD, and CREDENTIAL count anywhere in a name; TOKEN and KEY must be separate words, so length parameters such as `MAX_OUTPUT_TOKENS` do not count. PAT, PASS, PWD, and AUTH count only as a suffix with a prefix (`GITHUB_PAT` counts; `PWD` and `preferred_auth_method` do not). The same rule applies before independent environments are stored in the database.

Legacy "service-library definitions + `mcp_bindings` assignments" migrate under the [MCP Configuration Guide](MCP-CONFIG-GUIDE.md#legacy-database-migration): reads derive the result immediately; the first MCP write persists it. Migration does not change configuration files. Library-level toggles, "Update to library version," import candidates, and MCP takeover are retired. MCP does not count as pending synchronization in the overview.

The built-in default channel for both Claude Code and Codex is the official `native` command. brew appears only in observed detection results and is not the default.

## Rules and Sources Native Domain State

Assistant rule files are authoritative. Targets are main Claude (`~/.claude/CLAUDE.md`), main Codex (`~/.codex/AGENTS.md`), and the corresponding `CLAUDE.md` / `AGENTS.md` in each instance configuration directory. `rules:status` is read-only and write-free. For each target it reports path, existence, complete actual text, `base` (sha256 of file bytes, or `missing`), a byte-for-byte matching saved template or source rule (`matched_template` / `matched_source_rule`), and source-follow state (`source_follow`: which source rule last wrote the file, whether that version remains, and whether the source has a new version). It also includes saved `templates` and `source_rules`; without source rules, `suggested_sources` lists recommended sources, with `collection` identifying an already registered collection with the same name/address. Disabled assistants and instances are not probed. Symlink, nonregular, unreadable, or non-UTF-8 targets report only a reason and offer no writes.

`rules:apply` writes one actual target file at a time, requiring `--only` and `--base`. New content comes from one of four options: direct editing (`--value`), a saved template (`--template`), a source rule (`--source-rule <collection>/<name>`), or another target's actual text (`--from`). Before writing, reread actual content and compare with `base`; a mismatch reports "Modified externally" and leaves the file and database unchanged. Writes acquire the global exclusive lock, use file-byte CAS, roll back on failure, and audit only ids and digests. Before overwriting with a template, source rule, or copy, backfill: if nonempty existing content matches no saved template, source rule, or last source-written version, automatically save a backup template named with the target and time. Suspected credentials in existing content prevent database storage and therefore reject the overwrite. Direct editing creates no backup. Rules have no "Sync" or "Takeover" and do not produce "Pending sync."

Users choose rule sources (2026-09-29). Skill collections read root-level `rules/` by default; their `rules_path` may point to a subdirectory or `.md` file inside the collection, with paths escaping the root ignored. Separate sources may also be registered through `rules.sources.<name>.path`: a local `.md` file or directory. Each `.md` in that directory is one rule, excluding README, without recursion. They are read in place; changes take effect immediately, without copying or database storage. Sources with the same name as a skill collection are ignored. A collection's local source may itself be a skill folder containing `SKILL.md`; links point to that folder itself. Deeper `skill_paths` likewise link to the actual discovered directories.

Rule templates (`rule_templates`) are maintained through `rules:save-template` (revision CAS on edits) and `rules:delete-template`, writing only to the database without touching files or taking the apply lock. Rule content is not compiled into the program. Recommendations come from skill sources and share collection definitions, mirrors, and "Update resource library" with skills: git collections read `rules/*.md` from their data-directory repository mirror; local-directory collections read registered `rules/*.md` in place, with immediate updates, excluding `README.md`. They are read-only, never stored in the database, and the UI shows differences from existing target content before application. Applying a source rule records "target → rule id + written digest" in the database (`rule_source_applied`, an ownership record). If the source has a new version and the file remains the last written version, the UI offers "Update to new version." External edits are explained but not marked updatable. Applying content already identical to the source records follow state only, without changing the file. Writing other content clears the record. Auditing records rule id, digest, and git source commit. Author-maintained rules live in agent-skills `rules/`, moved with history from this repository's `agent-rule/rules` on 2026-09-23. Legacy shared rules used only to identify old database migrations are frozen in `engine-rs/assets/legacy-rules/`. `profiles:apply` no longer renders or checks instance rule files. Creating an instance copies a rule file only if the user selects "Carry over from the default environment" (`profiles:seed` through `rules:apply --from`); the Rules page can also copy from the main assistant.

Legacy shared + assistant-specific sources (`rules.shared` / `rules.claude` / `rules.codex`) are retired, as are hook and alias sources (see "Aliases Native Domain State" and "Hooks Native Domain State"). `sources:get/set` has been removed entirely. User-edited `rule_sources` content differing from built-ins migrates on writes into "Legacy rule source (Claude)" / "Legacy rule source (Codex)" templates, rendered from the old shared + corresponding assistant-specific sources. Reads derive the same result immediately. Migration neither changes actual files nor deletes old tables; `rule_target_bindings` no longer gates writes. Configuration backups export `rule_templates`; importing `rules.*` sources from old backups likewise converts them into legacy-source templates.

## Aliases Native Domain State

Managed blocks delimited by paired comments in `~/.zshrc` and `~/.zprofile` are authoritative for terminal shortcuts. Their `alias` lines are active shortcuts. User alias lines outside the block are listed read-only as "Other sources (not written by this tool)" and never changed. `aliases:status` is read-only and write-free. Per file it reports managed aliases (values for the tool's `alias name='value'` syntax; `null` values with original lines for other syntax), outside aliases, and `base` (block-body digest, or `missing`). Top-level `aliases` combines both files by name, reporting locations and consistency. `alias_recommendations` lists source recommendations, each with `source`; without source aliases, `alias_suggested_sources` lists the same recommendations as the Rules page. `alias_legacy` contains aliases saved by old versions but not active. If an rc file is a symlink, such as one managed by dotfiles, reads and writes use its final target and preserve the link. Broken links, nonregular or non-UTF-8 files, and unmatched block comments report only reasons and offer no writes.

`aliases:apply` changes one name at a time: add/rewrite (`--set <name> --value <value>`, optionally `--rename-from <old-name>` for in-place rename), remove (`--remove`), add a recommendation (`--recommended`), or add a legacy alias (`--legacy`). `--zshrc-base` / `--zprofile-base` determine the files to write; the UI supplies them for writable files. `~/.zshrc` is always written and created if missing. `~/.zprofile` is synchronized only if it already has a managed block, keeping the same syntax; without a block it is skipped and listed in `skipped`, never created or appended (user decision dated 2026-09-30, rationale below). Each file independently compares `base`; any mismatch rejects the whole operation as "Modified externally," leaving files and database unchanged. Only lines defining that name are replaced or removed; all other block lines and outside bytes are preserved. An empty block is removed with its two comments. Initial append adds only a missing newline, without an extra blank line; adding and then removing restores the original byte for byte. Values cannot contain single quotes, newlines, or suspected credentials; use `${VAR}` instead. Writes use the global exclusive lock, per-file atomic CAS, rollback of already written files on failure, and auditing of names and digests only. Aliases have no "Sync," "Takeover," or "Pending sync." The UI no longer has global timezone/language settings: files receive literals, with built-in defaults prefilled on creation.

**Why only `~/.zshrc` is written (tested 2026-09-30)**: every interactive zsh reads `~/.zshrc`. New Terminal/iTerm windows are login + interactive, reading `~/.zprofile` before `~/.zshrc`; tmux and some IDE terminals are non-login interactive and read only `~/.zshrc`. Only login noninteractive shells, whose stdin is not a terminal (such as UU remote term), read only `~/.zprofile`. Synchronization to `.zprofile` was added for such remote terminals on 2026-07-04. Machines already using it have managed blocks in both files and continue to synchronize; the tool no longer creates `~/.zprofile` for machines without a block.

When adding, editing, or renaming an alias, the dialog uses read-only `aliases:preview` below the one-line launch command to show actual rc paths and complete candidate text. Input changes or a newly read file baseline immediately invalidate old results; failed previews prevent saving. Dialogs for removal, recommendations, and saved legacy commands show the same preview before confirmation and block confirmation on failure. Discarding only a legacy database record explains that terminal files remain unchanged. After preview failure, close the operation, reread actual status, and reopen from fresh state, avoiding an old form acquiring a new baseline and overwriting external edits. Preview and writing share one plan; saving still rereads and validates under lock. Raw content may contain sensitive values and is displayed locally only, never stored in the database.

Recommended shortcuts are not compiled in. Skill-source root `aliases/*.json` supplies `timezone`, `lang`, and an `aliases` mapping; `{timezone}`/`{lang}` in values resolve from that file's fields. They share collection definitions, mirrors, and "Update resource library" with skills. Files are read in collection-name/file-name order, first occurrence wins for duplicate names, and structurally invalid files are skipped entirely. The author-maintained version lives in agent-skills `aliases/`, moved from this repository's `config/shell-aliases.json` on 2026-09-23. Recommendations appear only as "Recommended · Add," showing the resolved line and source; each requires confirmation (`aliases:apply --recommended <name>`, auditing the source). A same-named alias anywhere in either file, inside or outside the block, suppresses the recommendation. User-saved `alias_sources` entries differing from frozen old defaults (`engine-rs/assets/legacy-aliases/`, identification only), without the same name/value in actual blocks, appear as "Saved but inactive." They may be added (`aliases:apply --legacy`) or discarded (`aliases:discard-legacy --legacy <id>`, database only, removing the whole row when nothing remains). If a same-named block alias has a different value, show its current line; adding replaces it. Reads derive suggestions immediately; writes remove legacy aliases already present in the block before or after writing. Corrupt old tables suppress suggestions only. `alias_target_bindings` no longer gates writes and remains unchanged in the database. Backups exclude actual aliases and retain only old rows with inactive aliases as the `aliases.shell` source; imports show them as suggestions likewise.

## Hooks Native Domain State (Removed 2026-09-29; Historical Record Only)

Actual assistant configuration is authoritative for Hooks. Targets are main Claude (`hooks` in `~/.claude/settings.json`), main Codex (`~/.codex/hooks.json`), and corresponding `settings.json` / `hooks.json` files in each instance directory. `hooks:status` is read-only and write-free, reporting path, existence, actual hooks structure, `base`, and two suggestion types per target. Claude hashes only the `hooks` subtree (`missing` if absent), so other settings.json edits do not affect it; Codex hashes hooks.json bytes (`missing` if absent). Disabled assistants/instances are not probed. Symlinks follow the same decision as `agents:configure`: read/write the final target, perform atomic writes in its directory, compare target bytes using CAS, and preserve the link. Broken links, directories, nonregular files, non-JSON objects, or invalid hooks skeletons report reasons without offering writes. Official hook `type` values include `http`, `mcp_tool`, `prompt`, `agent`, and future types as well as `command`. Structural validation checks only "event name → array → matcher/hooks"; `command` also requires a nonempty command. Other types do not block the target: display them accurately, make them read-only in row editing, preserve entire entries on writeback, and permit direct changes through raw editing.

`hooks:apply` writes one actual target file, requiring `--only` and `--base`. Content comes from direct editing (`--value`, a complete hooks object subject only to skeleton validation), a cleanup suggestion (`--cleanup`), or a saved legacy hook (`--legacy`). Reread and compare actual content before writing; mismatch reports "Modified externally" and leaves file/database unchanged. Writes use the global exclusive lock, file-byte CAS, rollback on failure, and auditing of ids/digests only, never commands. Claude replaces only `hooks` in place and preserves other keys semantically, removing the key when empty; this and `agents:configure` own separate keys and do not overwrite each other. Codex writes hooks.json's `hooks` key and preserves other root keys. Hooks has no "Sync," "Takeover," or "Pending sync."

Structured or raw Hooks editing automatically calls read-only `hooks:preview` once row fields are valid or raw input forms a JSON object. Preview shares backend validation/rendering with writes and displays complete target paths and candidate text; input changes immediately hide old results. No-op edits explicitly state that nothing will be written. Preview creates no files or database; saving still revalidates actual files.

Built-in removed_signatures provide only "Cleanup suggestions." Matching legacy-signature `command` entries are listed individually and removed only after "Clean up" confirmation, with `base`. No matches means no display. User-saved `hook_sources` hooks differing from built-ins and absent from actual main-assistant configuration appear as "Saved legacy hooks (inactive)." Each may be "Added to actual configuration" (`hooks:apply --legacy`) or "Discarded" (`hooks:discard-legacy --legacy <id>`, database only, deleting the source row when empty). Already-active hooks are not suggested again. Reads derive suggestions immediately; writes to main targets remove database entries present in actual configuration before or after the write. Corrupt legacy tables suppress suggestions without blocking the Hooks page. `hook_target_bindings` no longer gates writes. Hook-source keys retire with `sources:get/set`. `profiles:apply` no longer renders instance hooks: it writes neither hooks.json nor the instance settings.json `hooks` key. Instance hooks are edited from actual files on the Hooks page; legacy instance fingerprints containing hooks remain recognized. Backups exclude actual hooks, retaining only inactive legacy hooks through `hooks.*` sources; imports show the same inactive suggestions.

`system:audit` is wired into the Rust dispatcher and aggregates agents/skills/mcp/rules/hooks/aliases/secrets and runtime/storage state read-only. The Secrets page first shows the storage path, then variables and origins. Entering or taking over values requires a selected external `.env` file with permissions `600`. Without an existing file, create one in place: `secrets:source --path <path> --create` exclusively creates a missing empty file with 0600 and missing parent directories with 0700. Existing files remain unchanged; creation inside the data directory is forbidden; a newly created file failing validation is deleted. Leaving "Create one" blank uses `~/.config/agent-manager/secrets.env`. If a connection form first receives an API Key without a secret file, it automatically creates that default file before saving and shows the destination beforehand. `secrets:status` `source.names` lists existing variable names without values, letting connection and independent-environment forms explain "Value exists: leave blank to keep it" or "No value yet: fill in to use."

Beyond variables referenced by MCP, `secrets:status` `provider_keys` lists credential variables referenced by connections and independent environments: where each is used, whether it has a value, and whether it comes from an external file or the process environment. It reports variable names only, never values, and performs no writes. Independent environments resolve values into their own configuration files (0600). `profiles:status` marks the field `purpose: "credential"` with its variable name. Changing the source value produces a mismatch; the card separately explains "The key changed; this environment still uses the old one" and offers "Write new key," rather than grouping it with ordinary differences or offering "Update definition from actual configuration." Cards also identify the source variable, destination file, and consistency with the secret file. SQLite stores only paths; status, logs, and backups contain no values. Historical database values show only a count and require a typed confirmation word to migrate explicitly; the old table is removed only after successful file writing. Settings "Configuration tools" links to client diagnostics, Aliases, and Secrets; rc managed blocks are authoritative for Aliases (see "Aliases Native Domain State"). Under the product decision dated 2026-09-12, Tools, snapshots (`snapshots:*`), and `system:converge` are retired, with pages, Tauri allowlist entries, and contract schemas removed. `system:refresh-upstream` is wired into the Rust dispatcher, probing agents/mcp/skills and caching in SQLite `upstream_probes`. Status for those domains reads freshness without writes or network; missing tables/rows return unknown. `--offline` is rejected.

Before "Write configuration," "Overwrite actual configuration from definition," or "Write new key" on a saved independent environment, `profiles:preview --only … --base …` uses actual secret values and the write plan to display complete target paths and candidate text. Potential credentials are viewable locally only. Failed previews prevent confirmation; cancellation performs no writes. Confirmation validates both original-file and candidate-content digests from preview. External file, definition, or secret changes that alter the candidate reject the write and require a new preview. Draft previews for new environments still retain variable references.

When editing a Provider and selecting existing independent environments to update, candidate previews explicitly read current secrets. A newly entered key is used only for read-only rendering until submission saves it to the external secret file. Each selected environment shows complete resulting files and returns original/candidate digests. Submission resolves secrets and rerenders; any digest mismatch rejects that environment's write. Unselected environments remain unchanged; saving only a Provider template does not change environment files. Existing CLI previews still show references unless the real-values option is supplied.

Backup import restores only database definitions and sources; it writes no actual assistant files and does not restore external secret files. Successful import directs users to preview and apply each item on its page. Overview "Sync all" handles only currently bulk-syncable items and is not a backup-restoration entry point.

SQLite core, Tauri bridge, Settings, primary resource-page layouts, Agent native lifecycle, Skills/MCP/Rules/Hooks/Aliases native domains, Runs SQLite operation history, and Python removal are complete. Built-in skill repositories are recommendations only (`skills:status.recommendations`); adding one makes it a user collection without automatically assigning it to any assistant. The Skills page also displays actual assistant-directory entries (`skills:status.installed`). Collections and Skill×Agent assignments support independent update, enable/disable, and removal. Enable uses content-addressed snapshots and safe symlinks; status remains read-only/write-free and real apply has process locking and operation auditing. History audits real operations through `operation_logs`; `log_retention_days` controls retention (0 disables automatic cleanup), and the execution center requires confirmation before clearing. Only two operation types can be undone (2026-09-29): skill assignment and enable/disable through inverse actions, and rule overwrites with saved backup templates through restoring the backup with normal write checks. Other writes retain no original content because assistant configuration often contains credentials and retaining it would violate the plaintext prohibition in database/logs. They cannot be undone automatically; the UI states this. Actual configuration is authoritative for Hooks (see "Hooks Native Domain State"); hook-specific `sources:get/set` is retired. The candidate based on `5a110be3` completed major real GUI E2E under the obsolete plan→confirm flow, which does not prove the new direct-apply flow. The Darwin x86_64 DMG acceptance on 2026-09-09—read-only mounting, copying outside the repository, no Python, sanitized paths, and startup within 5 seconds—predates current Rules/MCP/Hooks/Secrets and read-only `system:audit`, so it does not prove their current GUI workflows. Signing, notarization, arm64, Linux, Windows, and update publishing remain unverified.

Old DMG/GUI E2E evidence does not prove the current interaction. Current source, browser, isolated CLI, and uncommitted dirty-candidate DMG acceptance are complete. The final clean DMG was rebuilt after final commit `a01d0f5` and independently verified by the lead reviewer (commit, SHA256, and results in the [Delivery Receipt](goal-rust-gui.md)).

## Quota Sources

Assistant-card quota data reads local files only: no network, API calls, or installed hooks.

Claude selects the newer `checked_at` from two sources: `<data_dir>/usage/<encoded-config-directory>.json` (encode `%` as `%25` before `/` as `%2F`; no files are placed in assistant configuration directories), containing live statusline-script values with Claude Code's `used_percentage` and Unix-seconds `resets_at`; and `cachedUsageUtilization` in `~/.claude.json`, refreshed only when Claude Code explicitly checks quota, not during ordinary conversations. `<data_dir>/statusline.sh` writes the live file. Under the multi-account design, shared settings install it as each account's statusline; missing or corrupt content falls back to the cache. The configuration directory follows `CLAUDE_CONFIG_DIR`, with each instance reading its own.

Codex reads the last `rate_limits` in `<CODEX_HOME>/sessions/**/rollout-*.jsonl`, using that event's `timestamp`. Later events update file mtime, so using mtime would falsely report freshness.

Display rules: windows past their reset time show no percentage, since it belongs to the previous window; Claude Code's own statusline also drops them at reset. If the entire record is older than 24 hours, percentages turn gray with a question mark.

## Usage Statistics

`usage:status` reads aggregated results only and does not create a missing database. `usage:scan` reads session files and writes aggregates; `usage:clear` clears them for a restart. Both assistants' own session records supply data without network. Claude `assistant` event `message.usage` is incremental; Codex `token_count` event `total_token_usage` is **session cumulative**, so use `last_token_usage`. Its model name comes from earlier `turn_context` and must be persisted with scan state because an incremental scan cannot reread that earlier context.

Incremental scanning uses byte offsets: append-only JSONL keeps offsets valid. Process only through the last newline, because the assistant may be writing a partial final line. Local measurement: initial scan of 1.27GB / 181 files took 32 seconds; later incremental scans took less than 1 second.

Deduplication rules were checked against real CLI session files (claude 2.1.281 and codex 0.156.1 with a local fake endpoint):

- Claude `--resume` appends to the original file, but `--fork-session` creates a new file copying earlier replies with the same `message.id` and usage. Deduplicate by `message.id` **across all files**, storing an 8-byte digest key in `usage_seen_messages`. On first table creation, backfill already scanned portions of every file, so subsequent forks of pre-upgrade sessions are recognized. Truncated Claude files are reread from the start with deduplication protection.
- Codex counts `last_token_usage` only when cumulative `total_token_usage` changes; retransmission of the same total, such as quota updates, is not counted again. Copy-based forks and subagent files (metadata with `forked_from_id` or `thread_spawn.parent_thread_id`) begin with copied parent records, followed by a `thread_settings_applied` owned by the new session (`rust-v0.156.1` `session/mod.rs`, appended together with the copied prefix). Ignore prefix `token_count` events, using their cumulative value only as this session's starting point. Markers include `thread_id`; copied markers retain original ownership, so nested forks or resumed parents may leave parent markers in the prefix. Recognize only the marker whose `thread_id` matches this file's `session_meta.id`. If no owned marker exists in this segment, the first legacy marker without ownership ends it. Real 0.156.1 `codex exec fork` is reference-based, has its marker first without copied usage, and its actual marker `thread_id` equals the session id. At EOF without an ending marker: if the file changed within the last 30 seconds, do not consume the prefix and reread from its start next time, as it may be incomplete; otherwise treat it as an old version without markers and count normally because copied records cannot be identified. A truncated Codex file is not recounted from the start: resume after its current last complete line. Stopping inside a partial line would read its remainder as a fragment next time and miss usage.
- Independent-environment sessions live in their own configuration directories (Claude `<directory>/projects`, Codex `<directory>/sessions`) and are scanned the same way. Assistant identifiers are `claude:<instance>` / `codex:<instance>`; the UI shows "Claude Code · <instance>" and offers separate assistant filters. Third-party connections run only in independent environments; this usage was previously entirely omitted.

Aggregate by UTC hour into `usage_hourly`; the UI groups days in local time. Storage contains no timezone, so viewing the same data in another timezone does not misalign it.

After local-day aggregation, filters cascade "Time → Assistant → Model." Summary cards, missing-pricing notices, and detail tables must share one result set. Changing time clears assistant/model; changing assistant clears model, avoiding inapplicable downstream criteria. Filters affect loaded results only and trigger no scan or writes.

Costs are estimates, not bills. `usage.pricing` uses USD per million tokens, with built-in pricing for three official Anthropic models from the official pricing page, checked 2026-09-20 (cache writes 1.25×, cache reads 0.1×). Third-party pricing is blank for users to fill in. If any relevant price is missing, omit that whole bucket's estimate rather than substitute zero. Model names often contain dots (`gpt-5.6-sol`), while policy key paths use dots as separators; prices must therefore be written as the entire `usage.pricing` table, never as model-name subkeys.

## Assistant Runtime Parameters

`agents:configure` writes runtime parameters into an assistant's own configuration file, separately from lifecycle `agents:apply`, which executes shell commands. It supports Claude Code and Codex shapes, determined by executable name. Targets are `~/.claude/settings.json` and the `config.toml` referenced by the definition's `mcp_config` (default `~/.codex/config.toml`).

**Main Configuration Contains Only Official Accounts**: official-account and third-party credentials never share a configuration directory. Main assistant files (`~/.claude/settings.json`, `~/.codex/config.toml`) no longer receive third-party connections. `agents:configure --use <name>` returns `AGENT_MAIN_OFFICIAL_ONLY` before reading any file and performs no writes. Third-party connections run in independent environments/instances (see "Create an independent environment" below). Third-party configuration left by old versions or manual edits is displayed accurately with a mixed-use warning; users can "Return to official account" (`--use-default`, with normal backfill before switching).

Account classification asks "where does it connect, and whose credentials does it use?" Claude is third-party only when env has nonempty `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, or `ANTHROPIC_API_KEY`; Codex is third-party only when `model_provider` is not built-in `openai`. Models, aliases, and timeouts are settings on an official account (`current_config.current.official`). An official account with only a model also has `current.default` set to true; it is no longer labeled "Current actual configuration (unsaved)" or mixed use. In that case `--use-default` performs no writes, removes no model, and creates no import item. The earlier "any connection key exists" classification treated an official account's model as an unsaved connection; returning to official removed the model and created an import item (reproduced with real codex 0.156.1 on 2026-09-24: `auth.json` and login state were unaffected, but the model was removed). Claude status also reports top-level `model` as `settings_model`, the key `/model` saves; env `ANTHROPIC_MODEL` takes precedence. "Runtime settings" directly edits top-level `model` in both main configurations, prefilling actual values and removing the key when blank. Only the target assistant is changed, with baseline validation before write and field readback afterward. Existing Claude `env.ANTHROPIC_MODEL` still takes precedence.

Default-environment status lists account (official, or "Third-party connection · address," explicitly mixed with official credentials in main configuration), login storage (owned by the assistant, neither read nor changed by this tool; third-party mode explains it uses the configured token), model and source key, and automation level. Its "Account and login" tab contains the official account card and login check, plus the active main third-party connection when mixed; third-party connections also occupy a separate lower section (see "Assistant page"). "Return to official account" appears only for mixed use. Its dialog lists keys to remove, what is saved first, what remains untouched (official login, runtime settings, MCP, Hooks, other connections, secret variables), and restart/login requirements. Read-only `agents:preview-default` shows complete resulting `settings.json` / `config.toml` from actual files and the write baseline. Confirmation is disabled until preview succeeds; on error, close the old operation and reread actual status. Writing still revalidates the baseline and safely backfills unsaved third-party content first. The dialog also submits the complete-file digest from preview: any later byte change, even an unmanaged comment, rejects the write and requires a new preview so displayed text matches actual writing. Preview changes no files, database, or secret file.

**Connection configurations**: `settings.profiles` stores multiple third-party relay connection definitions for saving, testing, import/export, or creating independent environments. Each has an address, token variable name, credential header (`token` → Bearer through `ANTHROPIC_AUTH_TOKEN`; `api_key` → x-api-key through `ANTHROPIC_API_KEY`, both supported by relays), model, opus/sonnet/haiku/fable aliases (one action points all to the default model; undefined third-party aliases otherwise send Claude's original model names), subagent model (official `CLAUDE_CODE_SUBAGENT_MODEL`, stored as `subagent_model` and written to instance env only during independent-environment creation, excluded from main-connection recognition because official accounts may set it), and timeout. Deprecated `ANTHROPIC_SMALL_FAST_MODEL` is read only from old values; new connections omit it, and independent-environment creation renders its official replacement as a Haiku alias. Addresses permit `https://` or `http://` on any host; non-HTTPS warns that tokens travel in plaintext. Actual target files determine the current connection: `agents:status` compares each saved configuration's rendered fields against actual values and returns `current_config.current` (`profile` for a match; `default` for official accounts including model settings; otherwise "Current actual configuration (unsaved)," possible only for third-party connections). Database `settings.active` records only the last write and breaks ties between identical candidates. Returning to official clears all connection keys without residual variables.

**Writes**: `agents:configure --only <assistant> --base <digest>` accepts one operation: `--runtime <json>` changes only supplied runtime fields (`null`, `""`, and `false` remove the item; absent items remain untouched); `--use-default` removes connection keys only and returns to official; `--save-current` saves actual configuration as a connection without writing assistant files. `--use <name>` (including `--connection`) is disabled and always rejected. `--base` comes from status `current_config.base`, hashing owned content and, for Codex, the currently referenced provider table. A reread mismatch returns `AGENT_CONFIG_CHANGED` ("Modified externally") without changing files or database. Unreadable, nonregular, or unparsable files yield no base; the UI therefore disables writes. Symlinks write their final target while preserving the link. Secret file, assistant configuration, and database writes share one transaction, rolling back everything if any step fails.

**Backfill before returning**: if actual connection matches no saved item, save it before returning to official. If identity matches the last-written configuration (Claude: address + auth header; Codex: address + token variable in the still-owned table, or the same provider reference), backfill model, aliases, and timeout into it; otherwise create "Imported configuration (time)." User-owned Codex tables or built-ins use `provider_ref` only, without copying or ownership; returning to official removes only `model_provider` / `model`. When a Claude token matches no saved variable, write it into a selected external secret file and generate/return a variable name; otherwise return `AGENT_LIVE_TOKEN_UNSAVED`, letting the user select a file on Secrets or explicitly discard via `--discard-live-token`. If backfill cannot render actual content exactly, such as simultaneous AUTH_TOKEN and API_KEY, return `AGENT_LIVE_UNREPRESENTABLE` with reasons. After confirmation, `--discard-live` skips backfill and returns directly. Database and operation records store variable names only, never tokens.

**Ownership granularity** is key paths, not entire top-level keys. Owned Claude fields are `env.ANTHROPIC_BASE_URL`, `env.ANTHROPIC_AUTH_TOKEN`, `env.ANTHROPIC_API_KEY`, `env.ANTHROPIC_MODEL`, `env.ANTHROPIC_SMALL_FAST_MODEL`, `env.ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU,FABLE}_MODEL`, `env.API_TIMEOUT_MS`, `env.ENABLE_TOOL_SEARCH`, `env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`, `env.DISABLE_AUTOUPDATER` (official disable-auto-update setting), top-level `model`, `effortLevel`, `enableArtifact` (plus deprecated `disableArtifact`), `permissions.defaultMode`, and `attribution.{commit,pr}`. Hooks-domain content, user `permissions.allow/deny`, and other env variables remain unchanged. The baseline hashes only these paths. Even before the first tool write, existing values prefill the form and can be changed using that baseline.

All writes use Claude Code's own persistent keys, the same ones `/effort` and `/config` write. Default reasoning effort is top-level `effortLevel`, accepting only officially persistent `low`/`medium`/`high`/`xhigh`; `max` is session-only. Model-specific levels saved by `/effort` in `modelSettings` take precedence and are listed read-only. Disabling Artifact writes `enableArtifact: false`. Official session overrides `CLAUDE_CODE_EFFORT_LEVEL` and `CLAUDE_CODE_DISABLE_ARTIFACT` have highest precedence and are never written by this tool. Old versions' env entries for these are labeled "Override variables" and removed only through "Clean up override variables" (`--runtime {"claude_clear_env_overrides": true}`).

**Statusline** ownership is conditional. Runtime `statusline` set to `builtin` deploys `<data_dir>/statusline.sh` (0755) and points `statusLine` to it. Claude Code executes the command in a shell, so paths use single quotes. Legacy bare paths remain recognized as tool-owned and report `builtin-legacy`, with "Repair statusline" offered. A quoted pointer whose deployed script differs from the one this version ships (an upgrade changed it, or it was deleted) reports `builtin-outdated`; the Accounts page offers "Update statusline", which applies `builtin` again to redeploy the script. Status only reads the script and never replaces it. Returning to "Keep current" removes only the tool's own pointer, preserving user settings. Ownership depends on `statusLine.command` pointing to that deployed script; other targets are user-owned, neither cleared nor counted as external changes. Besides display, the script persists statusline `rate_limits` (see "Quota Sources").

**Secrets** follow instance/MCP semantics: the database stores only variable names; target writes resolve actual values. `settings.json` env is a literal mapping, without Claude variable expansion, so writing references would not work. Missing values reject writes rather than produce empty tokens. Files are written with 0600.

`settings.automation_mode` represents Manual, Smart automatic, and Fully unrestricted; Claude/Codex adapters render supported fields. Fully unrestricted changes assistant security defaults, so the engine enforces `--allow-yolo`: a patch selecting that level without the flag is rejected, and the UI asks for separate confirmation first. Writes acquire the exclusive lock and audit changed fields and variable names, never values.

**Configuration-file editing**: forms cover the common parameters above. Other settings (permission rules, `modelSettings`, Codex profiles and tables) can be edited as complete target text in "View actual configuration file" above the default card, collapsed by default; it may contain credentials. `agents:config-file --only <assistant>` reads path, format (`json` / `toml`), complete raw content including tokens as if the user opened the file, and full-file digest `base`. Missing files return empty text and `missing`; non-UTF-8 files return only a reason. `agents:edit-config --only <assistant> --file-base <base> --value <full-text>` first checks the whole-file digest. Mismatch, including assistant-generated changes, returns `AGENT_CONFIG_CHANGED` ("Modified externally"), leaves files unchanged, and refreshes the UI. Then validate parseability, requiring a JSON object; parse errors report line/column without raw text. Codex also rejects forms preventing complete configuration loading (see "Codex side" below). Valid text is written exactly without reformatting. Identical content is not written. Symlinks retain the link and write the final target; writes lock exclusively and audit changed top-level keys only, never values or complete text in the database. Only main Claude/Codex are supported here; independent environments follow instance definitions. Their cards may read actual path/text through `profiles:config-file --only profiles:<instance-name> [--file <file>]`: main configuration by default; Claude also supports `mcp` (`.claude.json`) and `rules` (`CLAUDE.md`), Codex `hooks` (`hooks.json`) and `rules` (`AGENTS.md`). Only these names are accepted, with explicit per-file selection/read. Refresh shows external edits; potentially credential-bearing text is collapsed by default and comes directly from files, not definition rendering. The UI uses CodeMirror for default-environment editing, with syntax highlighting, line numbers, search/replace, and JSON inline checks plus "Format" (two-space formatting only on click). The editor is a separate bundle loaded on expansion. Changes can be reviewed before writing.

Hooks/rules/MCP call `hooks:apply --value`, `rules:apply --from`, and `mcp:apply --action copy`, sharing their normal comparisons, symlink resolution, and audits. Items are independent: failure proceeds to the next, returning `copied` / `exists` / `absent` / `skipped` / `failed` with reasons. The instance domain creates missing configuration directories with 0700. Audits record items/results only, never content. Skills are excluded and assigned by environment on the Skills page. Tested on 2026-09-24 using isolated HOME and the compiled engine CLI: both instance types copied all five items, main bytes remained unchanged, instance files were 0600 and directories 0700, real `claude mcp list` / `codex mcp list` in each directory showed only the nonplaintext entry, and Codex loaded merged config.toml. A repeat returned only `exists` / `skipped` and left instance bytes unchanged.

Cards also support direct copying. Copies prefill address, model, credential variable, and unknown source-profile extensions. Names try `<original>-copy`, `<original>-copy-2`, and so on, within 64 characters. Values are neither read nor copied; default behavior saves only without switching current configuration. Users may edit the name and all visible parameters before submitting.

Connections support sorting and secret-free share JSON import/export. Sorting/import save definitions only, neither switching current connections nor writing assistant configuration. Shared content includes connection parameters and variable names, never credential values, auth files, or active state. Import validates format, assistant shape, name, URL, model, and variable names, then explicitly submits as "Save without enabling."

**Check login**: official login status is excluded from status, with no auth-content reads or official commands on every refresh. Accounts calls `agents:auth-status` once per official account, caching results for 5 minutes. By default it checks local files only because official commands themselves write configuration directories, as described below. Claude checks login records in `.claude.json`, with a missing file meaning logged out. Codex checks whether `tokens` or `OPENAI_API_KEY` exist in `auth.json`, skipping values; a missing configuration directory means logged out. Inconclusive local evidence reports "Unconfirmed"; only "Confirm" adds `--probe` to invoke official commands. The probe details below describe that step. Pre-write login checks are user-initiated and still invoke official commands.

Response `account` supplies Claude `oauthAccount` email, organization name, and subscription tier (`organizationType` + `organizationRateLimitTier`, such as `Max 5x`; official probes use `email`, `orgName`, `subscriptionType`) only to identify the account in UI, never database, audit, or logs. Codex commands provide no identity, so after confirming ChatGPT login the tool reads `tokens.id_token` `email` and `chatgpt_plan_type` from that directory's auth.json, the sole exception authorized 2026-09-28. Access/refresh tokens and API keys are skipped during parsing and never enter in-memory structures. No writes or network; missing files, including keychain-only login, or unrecognized content show login method only.

Both main "Official account" and instance cards offer "Confirm" plus copy-only login/logout commands. Confirm invokes read-only `agents:auth-status --only <agents:assistant | profiles:instance> --probe` once, checking login saved by this directory alone; instance commands include their `CLAUDE_CONFIG_DIR` / `CODEX_HOME`, main commands do not. Claude probes remove all process-environment sources ahead of `/login` (both third-party credentials, long-lived token, five cloud switches, `ANTHROPIC_PROFILE`, workload-identity federation variables, `CLAUDE_CODE_SIMPLE`, etc.). Official `--settings` cancels credentials, cloud switches, and `apiKeyHelper` declared by directory settings.json only for this subprocess; CLI arguments outrank that file without changing it. Otherwise those settings hide directory login. `ANTHROPIC_CONFIG_DIR` points to a nonexistent location because Anthropic profiles are not directory-isolated and an active federated profile makes official commands report login in every directory. Interpret `authMethod` and `apiKeySource`: `claude.ai` or `/login managed key` (Console) is official login. API keys, `apiKeyHelper`, or cloud sources remaining after directory cancellation originate only from managed settings and do not count. Also check `.claude.json` login-key existence (`oauthAccount`; Linux Console `primaryApiKey`), never values. `.credentials.json` also stores MCP OAuth, so existence is not account login; the official command is authoritative. Codex probes remove `CODEX_API_KEY` and `CODEX_ACCESS_TOKEN`; `codex login status` itself reads the latter, not the former.

Probe results return login presence, method (Claude subscription / Console / long-lived token / ChatGPT / API key), and reasons for uncertainty, without account, tokens, or raw file text. The tool writes neither database nor files. Official login is directory-scoped, including macOS keychain paths. Changing an instance directory or removing it warns that login does not move with it and should be logged out before disuse. `.claude.json` login keys are checked only for existence; values are skipped rather than stored in memory. On first invocation in a never-started Claude directory, empty or containing only tool-written MCP `.claude.json`, official commands add their own first-launch records and back up the original into `backups/` (tested; subsequent probes do not modify it). Every Codex invocation creates temporary directories under `CODEX_HOME/tmp`. These are official CLI behaviors; MCP external-change checks compare entry content and ignore such records. Consequently, page queries do not invoke them. Status `--version` probes point `CODEX_HOME` / `CLAUDE_CONFIG_DIR` to dedicated system-temporary locations; default login checks use local files only (isolated-HOME test on 2026-09-29: all queries left the user directory unchanged). Every branch above was checked with real claude 2.1.281 under an isolated user. Official login in a third-party instance reports `mixed`, asking for logout or another directory; third-party instances offer no "Copy login command." Ordinary connection saving, sorting, import/export, and runtime settings never write auth files. Third-party connections run only in independent environments, keeping official login and third-party values apart. Login/logout entries only copy official CLI commands, never execute them. Instance commands explicitly include the right `CLAUDE_CONFIG_DIR` or `CODEX_HOME`; users must verify the target in a terminal and run them manually.

`agents:status` also parses Claude settings.json / Codex config.toml read-only, reporting actual provider, address, model, credential presence, and runtime fields in sanitized `observed.current_config`, plus write baseline `base` and content-recognized `current`. It also returns `last_written`, token-unverifiable `unverified`, and `drifted_from` when identity matches the last write. Claude `credential.saved_var` identifies the saved variable matching the actual token. Nonpreset automation reports `custom` with original values in `automation_raw`. Status writes nothing, returns no token/API-key text, and creates no database profile. Symlinks read final targets; broken links, nonregular files, oversize content, and malformed content use fixed fail-closed states. Current connection, runtime parameters, and prefilling read actual values. Immediate write summaries list changed keys only, followed by complete actual-file previews. After successful `agents:configure`, the UI must reread `current` matching the target, or every patch field matching actual values, before reporting success.

Main-assistant status adds `observed.credential_overrides`: external settings that override or constrain main official accounts but are not managed here. It lists origins and variable names only, never values. Sources:

- Shell startup files (`~/.zshenv`, `~/.zshrc`, `~/.zprofile`, `~/.bashrc`, `~/.bash_profile`, `~/.profile`, counting `NAME=` / `export NAME=` but not comments or alias assignments) and process environment. Claude checks `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_OAUTH_TOKEN`, five `CLAUDE_CODE_USE_{BEDROCK,VERTEX,FOUNDRY,ANTHROPIC_AWS,MANTLE}` switches, `ANTHROPIC_PROFILE`, `ANTHROPIC_FEDERATION_RULE_ID`, and `ANTHROPIC_CUSTOM_HEADERS`. Codex checks `CODEX_API_KEY` (noninteractive entries such as `codex exec`) and `CODEX_ACCESS_TOKEN` (all entries), both preceding auth.json login. Exported `CLAUDE_CONFIG_DIR` / `CODEX_HOME` redirect the assistant, disabling main-directory settings/login. Tool-written `alias name='…'` launch commands are not exports.
- Main Claude settings.json `apiKeyHelper` and env cloud switches, long-lived token, `ANTHROPIC_PROFILE`, and extra headers. Main third-party addresses/credentials are covered by mixed-use warnings.
- Claude managed settings at official fixed paths (macOS `/Library/Application Support/ClaudeCode`, Linux `/etc/claude-code`, including `managed-settings.d/*.json`, highest precedence): the same env fields plus third-party addresses/credentials, `apiKeyHelper`, `forceLoginMethod`, and `forceLoginOrgUUID`. Either login constraint blocks third-party-credential sessions at startup. macOS profiles and Windows registry are not inspected.
- Active federated Anthropic profiles: `~/.config/anthropic/active_config` points to `configs/<name>.json` with `authentication.type` set to `oidc_federation`. Official WIF documentation says this file has no secrets and precedes `/login`. Profiles logged in through `ant auth login` follow `/login` and are not warned about.
- Main Codex config.toml top-level `openai_base_url` / `chatgpt_base_url` override built-in openai/ChatGPT backend addresses, sending official credentials there. `forced_login_method` / `forced_chatgpt_workspace_id` reject another login method; Codex logs out existing incompatible login when `codex exec` or the interactive UI starts, empirically deleting auth.json.
- Codex system files (`rust-v0.156.1` layering, Unix `/etc/codex`): config.toml is below main configuration and warns about the same keys plus non-openai `model_provider` only when main omits the key. Legacy managed_config.toml is the top layer, where the same fields remain effective (tested: its `openai_base_url` overrides main and receives official credentials). requirements.toml includes non-openai `model_provider`, `chatgpt_base_url`, `allowed_login_methods`, and `allowed_chatgpt_workspaces`. macOS-profile-delivered settings are not inspected.

The workbench reports each origin and effect without changing those files.

Each instance `profiles:status` adds `observed.system_overrides`: system settings that directory isolation cannot block, again origins/key names only. Instances cancel shell-inherited credentials in their own configuration, but system settings affect every configuration directory:

- Claude managed settings, as above. Tested env overrides instance settings.json address/token, and `forceLoginMethod` blocks third-party-credential instances at startup. Official instances also report active federated profiles because `~/.config/anthropic` is not directory-isolated.
- Codex third-party instances report only fields that replace their provider: a different `model_provider` in `managed_config.toml` or `requirements.toml` (tested: the latter redirects to the organization's address), and same-named `requirements.toml` `model_providers` definitions that replace the entire instance provider. Before instance files exist, compare with the intended `agent-manager`. Official instances report the same system fields as main, resolving precedence against their own config.toml.

Cards explain each consequence, explicitly stating when login constraints block a third-party instance.

Clicking opens a precisely filtered palette; a second Enter/click opens complete-file confirmation, and writing follows confirmation only. **Codex side** writes the same config.toml as MCP, splitting ownership by sections. Here the tool owns nine top-level keys: `model_provider`, `model`, `approval_policy`, `sandbox_mode`, `approvals_reviewer`, `model_reasoning_effort`, `model_context_window`, `model_auto_compact_token_limit`, and `web_search`; plus tool-written `[model_providers.*]` sections/subtables recorded in `agent_settings_bindings.owned_providers`. No management comments are written. Referenced connections (`provider_ref`) write only `model_provider` / `model`; referenced tables are unowned, neither written nor deleted. Legacy `# [agent-manager:managed]` before provider sections identifies ownership during migration only and is removed with the old section on next write. All other lines, including comments, user keys/providers, and MCP `[mcp_servers.*]`, are preserved exactly. Text-level editing replaces top-level keys in place or inserts them before the first table, preceding its attached comments; table sections are replaced whole.

Main configuration contains official accounts only and receives no third-party connections; recorded `[model_providers.*]` sections are removed only during "Return to official account." Third-party Codex runs in independent environments, with credentials as described above. Skipping permission confirmation writes `approval_policy = "never"` and `sandbox_mode = "danger-full-access"`. Reasoning effort offers all known Codex client levels (`rust-v0.156.1` `ReasoningEffort`: none, minimal, low, medium, high, xhigh, max, ultra, persistent); supported levels depend on the model.

Codex validity is global: one hard config.toml error prevents all commands, including interactive UI and `login status`, from starting. Status lists known fatal forms in `current_config.config.fatal_issues` with prominent workbench warnings; `agents:edit-config` rejects them. Only forms confirmed by `rust-v0.156.1` source and individually reproduced as "Error loading configuration" with real 0.156.1 `login status` qualify: `approval_policy = "untrusted"`; sandbox_mode outside its three values; boolean web_search; top-level profile; `ollama-chat`; redefining built-ins openai/ollama/lmstudio; provider `wire_api = "chat"`; missing custom-provider `name`; empty `auth` command; and `auth` together with `env_key`, `experimental_bearer_token`, or `requires_openai_auth = true`. Forms loading successfully in the same tests are excluded: unnamed Bedrock built-in address override, `approval_policy = "on-failure"`, or `auth` alongside `requires_openai_auth = false`. Instance provider `name` uses the display name, falling back to instance name when empty or exactly `OpenAI`, which Codex identifies by name as built-in openai.

The statusline exists only on Claude; Codex does not have that mechanism.

**Availability check** (`agents:check --only <assistant> [--use <connection>]`) is the sole assistant command that proactively uses network, only when explicitly clicked; other commands are network-free. It is read-only, touching no configuration or active connection, with no database writes except audit. Missing address/model/variable/value rejects before requesting and explains what is missing. Referenced Codex `provider_ref` addresses and token variables come from the referenced config.toml table. Without `env_key`, or with file-based `experimental_bearer_token` or command-generated `auth`, credentials are not read; official `requires_openai_auth` login is not checked on the user's behalf either, with reasons explained. When a table is absent, local `ollama`/`lmstudio` use known default addresses without tokens. Built-in openai uses Codex official login (`OPENAI_API_KEY` is no longer a Codex credential source in 0.156); Bedrock uses AWS signing. Neither is checked by borrowing other variables for a request. Other missing providers explicitly report "No longer in config.toml." Requests follow protocols: Claude `{base}/v1/messages`, Codex `{base}/responses`. HTTP results become actionable explanations: 401 invalid token; 404 wrong endpoint shape; 429 correct address/token but rate-limited, counted as pass; HTML instead of API response suggests firewall/Cloudflare; 403 explicitly allowing coding-assistant clients only, such as Kimi Code membership, means the tool cannot check and does not impersonate clients. Tokens reach curl through 0600 temporary `--config` files, never command lines visible to local `ps`; upstream errors are sanitized before leaving the engine.

Because third-party connections actually run in independent environments, `agents:check --only profiles:<instance>` checks them too, using definition address, credential variable (Claude `${VAR}`, Codex `env_key`), and model consistent with written configuration. Official instances lack third-party endpoints and receive no proxy requests; users are told to verify with their launch command in a terminal. Third-party cards offer "Test" and show results in place.

**Fetch model list** (`agents:models`) follows the same rules: network only when "Fetch model list" is clicked, read-only except audit, with credentials passed to curl through 0600 temporary files. Targets may be saved connections (`--only <assistant> --use <connection>`), independent environments (`--only profiles:<instance>`), or unsaved drafts (`--draft {"kind","base_url","token_var"}`). The engine resolves credentials from secret sources without passing values through UI; missing values reject before requests. Candidate URLs remain on the connection's host. Claude first tries `{base}/v1/models`, `{base}/models`, then removes compatibility suffixes `/anthropic`, `/api/anthropic`, or `/apps/anthropic` and tries the same vendor's OpenAI `/v1/models` / `/models`. Codex tries `{base}/models`, then `{base}/v1/models` when base lacks `/v1`. The same credential goes in both `x-api-key` and `Authorization: Bearer`, as official apiKeyHelper does; Claude adds `anthropic-version`. 404/405 advances to the next candidate; other errors use availability-check explanations. If all fail, report "This endpoint does not provide a model list," never invent names. Results populate only model/alias dropdown candidates in connection and environment forms.

**Vendor presets** (`app/src/lib/connectionPresets.ts`) are form helpers only, not deployment logic. Selection fills address/model/aliases, still editable. Inclusion requires vendor-operated service plus an endpoint in official documentation. On 2026-09-24 this updated Z.ai Claude to glm-5.3 with recommended timeout and added MiniMax. Later, CC Switch coverage informed additions for Kimi Code membership (Claude, official x-api-key requiring preset header support, with fable/subagent models), Ark Coding Plan (Claude), Xiaomi MiMo and Meituan LongCat (both shapes), and Step Plan (Claude, domestic/international), totaling 25. **Check balance** (`agents:balance`) supports only vendor-documented balance APIs: DeepSeek "Query balance" `GET /user/balance`, and Moonshot/Kimi Open Platform domestic/international "Query balance" `GET /v1/users/me/balance`.
