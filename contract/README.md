# Engine Contract v1

> Current general launch APIs: `launch:catalog/build/list/save/delete/run` are independent of accounts. Saved recipes are inactive app data and do not require a local application. Building is read-only; Agent Manager does not write shell configuration. Graphical launch requires a separate confirmation. See [launch configurations](../docs/subsystems/launch-configurations.md).

> Current scope: [Extensions only](../docs/EXTENSIONS-ONLY.md) supersedes the historical account, assistant lifecycle, authentication, runtime, and alias contracts below. Those domains return `FEATURE_RETIRED`; Tauri rejects them at its command whitelist. `resources:targets` accepts no arguments and returns `{domain:"resources", targets:[{id,name,group,kind}]}` from immutable registration metadata, without opening authentication/settings files or executing assistants. `system:discover` accepts only `--only skills`; audit and upstream refresh exclude assistants and aliases. Backups omit account/alias policy, imports cannot change it, and legacy alias sources are skipped. Secret editing is limited to MCP-specific variables.


`contract/engine-v1/` describes the JSON envelope, status, actions, and policy shapes shared by CLI and Tauri. The implementation entry point is `engine-rs`; the repository does not depend on Python or the old shell pipeline.

`native-manager.db` stores this tool's definitions, preferences, and saved but inactive alternatives. Actual contents of assistant configuration files are authoritative for active configuration. Settings are in SQLite `app_settings`. Policy reports only `builtin` or `sqlite` ownership; there is no three-layer JSON model, writable settings JSON, or profile synchronization layer.

Policy writes use `--layer local`: `local` is the write-target argument, while the persisted source is `sqlite`. Reads with no database and status/query calls perform zero writes.

Agent collections and per-Agent Skill actions cover add, edit/update, enable, disable, and remove. Saving a definition executes no action. `apply` directly executes engine-returned actions with preflight, exact scope, locking, external-change detection, CAS/conditional rollback, and auditing. Removing management and uninstalling are distinct actions.

MCP uses actual entries in assistant configuration files. `mcp:status.targets` lists each assistant's MCP file; `elements` groups entries by service name, with env/header references preserved, literals masked as `<literal>`, non-credential unmodeled official fields preserved, other fields `<hidden>`, and a digest `base` per entry. `mcp:apply` acts on one entry: `add` (`--spec`), `edit` (`--spec --base`), `enable`/`disable`/`remove` (`--base`), `copy` (`--to --base`; overwriting the same name requires `--replace --to-base`), or `forget` (delete an unassigned saved definition). Re-read and compare `--base` under the lock before writing; a mismatch reports an external modification and leaves both files and database unchanged. Disable follows `targets[].disable_mode`: Codex/OpenCode write official `enabled = false`; Claude Code removes the entry and stores a disabled snapshot in `mcp_saved`, without plaintext that resembles credentials. Additional hints, such as variables moved to external storage or fields omitted during copy, are returned in envelope `warnings`.

Public `*:plan` and `--dry-run` entry points are retired and rejected.

The lightweight desktop retires every `usage:*` command (including dotted aliases)
with `FEATURE_RETIRED`, before database, secrets, or assistant-file access. Legacy
account usage fields are null. Runtime patches reject `statusline: "builtin"`;
explicit main-account cleanup preserves custom commands and uses the normal CAS
baseline. Existing sessions and database rows are preserved.

`agents:status --metadata-only` returns normal account metadata with a null version
and does not execute assistant version probes. `skills:status --collections-only`
returns collection metadata and installed/unmanaged discovery without constructing
per-skill elements or fingerprints; it omits the deferred `discovery_inbox` health
field. Both flags are read-only and can be combined with `--offline`. Full status
remains available for explicit validation and write planning.

Read-only `system:discover` scans existing local agents / skills not yet managed. It supports `--only agents|skills`, performs zero writes and network requests, and does not take the apply lock. MCP entries appear directly in `mcp:status` and do not use discovery/import. Each candidate has a `manage` classification: `native` (identify official paths and native installations without taking over), `symlink` (manage an external resource through a symlink), `collection` (use an existing collection's adoption workflow), `register` (register an assistant CLI definition), or `cleanup` (suggest removal of residues such as broken links). Like `system:audit`, this is a read-only aggregate; frontend types currently fix its data shape, to be formally specified in contract v2.

`profiles:status/apply/adopt` manages assistant instances. An instance is an `agents.definitions.<id>` entry with a `profile` section in the saved layer; the real environment has only a directory and launch command. Skill assignments and per-assistant MCP entries therefore apply directly. Actual contents are authoritative for generated instance files. Read-only status returns `observed.base`: Claude hashes the `env` and `model` fields in settings.json; Codex hashes the bytes of `agent-manager.config.toml`; a missing file is `missing`. `fields` compares definition and actual values per field (`same`/`differs`/`missing`/`unresolved`), with credentials `<hidden>`. Differences produce `drifted` and an `adopt` action. `apply --only profiles:<id> --base <base>` writes the definition to actual files: Claude changes only declared env variables and `model`, preserving user-added env, root fields, and hooks, and removing formerly owned variables removed from the definition. Codex writes the whole `agent-manager.config.toml`, layered by launch argument `-p` to avoid MCP-owned `config.toml`. Baseline mismatches are rejected as external modifications; `--allow-takeover` is retired. Symlink targets are written through to the final file. `adopt --only profiles:<id> --base <base>` reverses the direction, writing actual values to the instance definition in the database only; if credentials differ from referenced variable values, it reports the mismatch without storing plaintext. Directories use mode 0700, files 0600, with atomic replacement and rollback on transaction failure. Authentication persists only `${VAR}`: Claude resolves it during apply because its client does not expand references, with file permissions protecting values; Codex writes only the `env_key` variable name. Configuration directories must be under HOME, outside the main-instance and data directories, and not symlinks. Endpoints allow https and http, matching connection configuration. For instance definitions, `agents:status` does not read the main directory's configuration or login; `profiles:status` reports the instance's own status.

Skill collection definitions add `source_path`, mutually exclusive with `url`. Local-source collections do not create content snapshots: assistant links point directly to the registered source and reflect external updates. Only after the source root becomes a managed baseline may those links be overwritten or removed on disable; unregistered external paths still fail closed. Collection `update` for local sources does not access the network or clone; it rescans the source, refreshes fingerprints, and repairs enabled links.

`skills:status` also has two read-only fields. `recommendations` contains compiled-in source recommendations, not elements: they are excluded from pending synchronization and upstream checks and are not automatically downloaded. Add saves the recommendation's `definition` as an ordinary collection definition without assistant restrictions or assignment. `installed` lists actual entries in assistant skill directories using the same scan/classification as `system:discover`, with `managed` identifying this tool's links. If the older automatically persisted `agent-skills` collection is unchanged and has never been applied (no `skill_bindings`), reads treat it as a recommendation. `open_write` removes it from policy and records `skills:retire-builtin`. Applied or modified collections remain user collections.

`rules:status` returns actual full text, `base` (file-byte sha256, or `missing`), and matching templates per target (main Claude/Codex and instance rule files). It also returns saved `templates`, `source_rules` (`rules/*.md` from skill sources, never persisted in the database), and `suggested_sources` when no source rules exist. Each target has `matched_source_rule` and `source_follow` for source tracking and new-version availability. `rules:apply` requires `--only` and `--base`, with exactly one content source: `--value`, `--template`, `--source-rule <collection>/<name>`, or `--from`. Reject mismatched `base` as an external modification. Before overwriting with a template, source rule, or copy, preserve existing content that matches no known content as a backup template. `rules:save-template` takes `--name --value` for creation, plus `--template --revision` for modification, and returns `{domain, template}`. `rules:delete-template --template` returns `{domain, deleted}`. Both write only the database. Rule source keys were retired with `sources:get/set`.

`hooks:status` returns `observed.hooks`, `hook_count`, `base`, `cleanup`, and `legacy` per target (main Claude settings.json `hooks`, main Codex hooks.json, and instance equivalents). Claude hashes only the hooks subtree; Codex hashes file bytes; absence is `missing`. `cleanup` suggests removals matching built-in legacy signatures. `legacy` contains hooks saved in the old database but absent from actual main-assistant configuration and appears only for main targets. `spec.scope` is `hooks-key` or `whole-file`. `hooks:apply` requires `--only` and `--base`, with one of `--value <hooks JSON>`, `--cleanup <id>`, or `--legacy <id>`; mismatches are rejected as external modifications. `hooks:discard-legacy --legacy <id>` writes only the database and returns `{domain, discarded, source_removed}`. Read and write symlinks through to the final file; reject broken links and directory targets. Hook `type` is not restricted to `command`: other types receive structural validation and are preserved; cleanup suggestions match only `command`. `--allow-takeover` and hook source keys are retired.

`aliases:status` uses actual lines in managed blocks in `~/.zshrc`, `~/.zprofile`, and `~/.bashrc`. Elements are ordered with the primary target first: new commands go to `~/.bashrc` for bash `$SHELL`, otherwise `~/.zshrc`; on Linux with no `$SHELL` and only `~/.bashrc`, use bash. Other files synchronize only if they already have a managed block. The additional write-baseline argument is `--bashrc-base`. On Windows, the sole target is script directory `aliases:cmd`: one `.cmd` per command in `~/.agent-manager/bin`. This tool's scripts are decoded to the same `entries`; the baseline is `--cmd-base`, and `spec.kind` is `cmd-dir`. `observed.on_path` says whether the directory is on user PATH; if not, `path_command` and `path_manual` provide a command and manual steps for the user, without registry writes. Previewed script removals have `deleted = true`. Each file's `observed` contains managed `entries` (`{name, value, line}`; unrecognized syntax has `value = null`), read-only outside-block `external`, and `base` (block-body digest, or `missing`). Top-level fields also include `aliases` (merged by name, with `targets` and `consistent`), `alias_recommendations` (source `aliases/*.json`, each with `source`; omit names present in any file), `alias_suggested_sources` when no source aliases exist, and `alias_legacy` (old `alias_sources` entries absent from actual blocks with the same name and value). `aliases:apply` requires at least one `--zshrc-base` / `--zprofile-base`; write only specified files and compare each baseline, rejecting the entire operation on any external mismatch. Exactly one operation is required: `--set <name> --value <value>` (optionally `--rename-from <old-name>`), `--remove <name>`, `--recommended <name>`, or `--legacy <id>`. `aliases:discard-legacy --legacy <id>` writes only the database and returns `{domain, discarded, source_removed}`. `--only`, `--allow-takeover`, and `sources:get/set` are retired; the whole `sources` domain is outside the command surface.

`aliases:preview` accepts the same arguments as `aliases:apply` and returns read-only `{files, skipped}`. Each `files` item gives the changed `target`, actual write `path`, `exists`, and full candidate `content`; unchanged targets are in `skipped`. Preview takes no write lock and creates no file or database. Apply still re-reads and validates file baselines.

Schemas: `envelope.schema.json` (response), `element.schema.json` (elements and actions), `status.schema.json` (status), `apply-result.schema.json` (execution), `policy.schema.json` (policy), and `runs.schema.json` (SQLite history and clear results). `agents:configure` writes assistant runtime parameters to its own configuration, separately from lifecycle `agents:apply`. It requires `--base <current_config.base>` from `agents:status` and a `--runtime <json>` patch; optional arguments are `--preview-file-base` (full-file digest from `agents:preview-runtime`) and `--allow-yolo`. It returns `{domain, action, element, target, mode, active, current, changed, base, statusline}`. Rejections: `AGENT_CONFIG_CHANGED` (external modification) and `AGENT_MAIN_OFFICIAL_ONLY` (`--use`, `--connection`, `--use-default`, `--save-current`: main accounts allow official logins only; create a separate account for third-party endpoints). Rejections leave both file and database unchanged. The 2026-09-28 multi-account design retired `agents:preview-default`, `agents:check`, `agents:models`, `agents:balance`, `agents:config-file`, `agents:edit-config`, `profiles:config-file`, and `profiles:shared-preview`; calls return `UNKNOWN_VERB`. The plan/profile/converge/snapshots and logs schemas are retired and outside the current contract.
